## Closed ChangeIntent v1 contract

The internal v1 envelope is canonical LF UTF-8 JSON with recursively sorted
object keys, no insignificant whitespace, duplicate keys, unknown fields, or
non-finite values. Its identity is SHA-256 over those exact bytes. It contains
or exactly references:

- schema/profile and deterministic intent identity;
- immutable authority, accepted-decision, tranche-lock, snapshot, R1.0
  baseline, and scope identities;
- objective and exact locked family/operation target;
- base commit/tree, clean-worktree observation, package lockfile identity,
  catalog/source revision, and dependency preconditions;
- canonical task-local proposed patch identity plus every proposed
  after-image identity, with no access-bearing locator;
- canonical owners and the exact graph-derived proposed write set;
- generated projections, affected packages, relations, proof/evidence made
  stale, required checks, and risk-selected review/manual obligations;
- operation effect classes, compatibility/version effects, rollback/recovery,
  and confirmation policy;
- readiness values only from `not-applicable`, `unknown`, `blocked`, or
  `proved`, with exact evidence for each `proved` claim;
- invalidation rules for authority, lock, source, worktree, patch, after-image,
  dependency, graph, proof, disclosure, review, and base drift; and
- an optional completed result that binds actual head/tree, canonical diff,
  changed paths, operation journal, deterministic results, reviewed inputs,
  and the original envelope digest.

Preview records are read-only and grant no mutation authority. A completed
record cannot change its preview fields. Any precondition drift, actual path
or byte mismatch, undeclared projection, incomplete closure, failed check,
missing risk proof, or result mismatch fails closed and requires a new
envelope.

For a new committed R1 family absent from the current catalog, the producer
must evaluate the exact locked Core contract and proposed after-images in an
isolated task-local preview, compile the proposed owner graph, and derive the
write/affected closure from that preview plus repository conventions. It may
not require the family to exist in the current catalog, infer a family from a
filename, or accept a request-maintained closure. The fixed 53-family snapshot
and tranche registry remain the only family-admission source.

For an existing family, the producer must compose the canonical semantic diff
and affected closure without allowing caller-selected version, proof, owner,
or path facts. Generated files may appear only as owner-derived projections in
the same envelope. They never become canonical inputs.

Repository-retained proof writes use the internal effect class
`evidence-retention-write`. That class means only an atomic evidence-root
addition derived from the exact proof owner and executed source. It is not a
canonical product-source write, cannot rewrite historical evidence, and
cannot claim acceptance. This is the minimum Architecture vocabulary
correction needed to classify the already required R1 evidence-only child
honestly.

## R1 operation binding

The corrected continuous verifier applies these boundaries:

- `r1-lock` is a read-only `explanation-only` operation. It may produce a lock
  and ChangeIntent prerequisites, but it writes no repository file and does
  not authorize implementation.
- `component-implementation` requires the exact accepted lock and a preview
  envelope whose locked family, proposed write set, affected closure, checks,
  review route, and confirmation policy match the operation. The actual result
  must bind the same envelope before the operation can pass.
- `retained-evidence-acceptance` requires an
  `evidence-retention-write` envelope for the exact evidence-only Git child,
  every retained artifact/proof relation, independent review where selected,
  and the verifier result. It cannot accept evidence by itself.
- `routine-git-operation` may act only on a prior passing verifier result and
  its exact ChangeIntent/result identities. It cannot relabel component,
  authority, package, dependency, evidence, generated, or release paths as
  administrative work.
- Project-only mutations bind their separately accepted Project preview and
  result. They do not become repository ChangeIntent writes.
- Intermediate protected merges bind the complete required hosted check and
  review set for the exact head/base. Npm publication and the final R1-exit PR
  merge remain outside the standing envelope and require Andrew's separate
  exact authorization.

The ChangeIntent producer is a preview/validation surface, not an apply
engine. This decision does not enable G2.5 project mutation, G2.6 allowlisted
proposals, consumer-project writes, or arbitrary agent patches.
