## 2. Findings, ranked by severity

### High

**H1. PreviewTrigger steals focus whenever the preview opens, by hover or by keyboard focus.**
- **Where:** `overlays.mjs:362-369` and `:501`.
- **Cause:**
  - `PreviewContent` renders a React Aria `Dialog`, and that component always focuses itself when it mounts (react-aria `useDialog`).
  - React Aria's own Popover deliberately skips auto-focus when `trigger === 'PreviewTrigger'` (`Popover.mjs:134`). Its design keeps focus on the link, and Tab moves into the preview (`usePreviewTrigger` handling of Tab on the trigger).
  - The inner dialog also strips the outer popover's `role="dialog"`.
- **Reproduction:**
  1. Click into a text input.
  2. Rest the mouse on a preview link for the delay.
  3. Focus moves to `.muxui-preview-content` and anything typed is lost (probe value `p1c_activeAfterHoverOpen: "muxui-preview-content"`).
  4. Separately, Tab onto the trigger and wait: focus again jumps into the preview (`p1b`).
- **Effect:** this is a focus change triggered just by focusing or hovering, which conflicts with the catalog line "Delegate ... keyboard handling to RAC PreviewTrigger". The playground test comment documents the theft as expected behaviour (`browser.test.mjs:387-389`).
- **Unaffected:** focus restore after closing works, and I saw no reopen race like the Autocomplete one (`p1b_previewOpenAfterEscape: 0`).
- **Verified by:** browser probe.
- **Suggested fix:** drop the inner `AriaDialog`. Pass `aria-label` / `aria-labelledby` to the `AriaPopover`, so React Aria's own `role="dialog"` takes the name without auto-focus. Then add a browser test that `document.activeElement` stays put on hover-open and on focus-open.

**H2. Dismissing a Toast with the keyboard drops focus to `<body>`.**
- **Where:** `overlays.mjs:708`.
- **Cause:**
  1. On close, the retained exiting toast gets `inert`.
  2. Chrome's focus fixup then blurs the focused dismiss button. My probe confirmed `inert` alone causes this; `aria-hidden` alone does not.
  3. The blur makes React Aria's `useToastRegion` handler for focus leaving the region null out `lastFocused` and `focusedToast`.
  4. So neither of React Aria's recoveries runs: moving focus to the next toast, or restoring focus to the element focused before entering the region.
- **Reproduction:** focus `#after`, add two toasts, focus the first dismiss button, press Enter. Focus is `[BODY]` after 20 ms and stays there. Dismissing the last toast also leaves `[BODY]` instead of restoring `#after`.
- **Effect:** contradicts the catalog line "RAC owns ... focus".
- **Verified by:** browser probe.
- **Suggested fix:** before applying `inert` / `aria-hidden`, move focus yourself if it is inside the exiting toast (to the next toast, otherwise the element focused before the region). Or keep the exiting record out of the focus-managed list without `inert`. Add a test of keyboard dismissal focus.

**H3. A declarative `<Toast>` is torn down and re-added on every parent render unless every prop is referentially stable.**
- **Where:** `overlays.mjs:809-823`. The effect depends on `message`, `title`, `onDismiss` and `className`.
- **Reproduction:** `<Toast message="Saved" onDismiss={() => {}} />` inside a parent that re-renders. After each render the old toast node is disconnected and a new key is added (`j1_sameToastNode: false`). A JSX `message` does the same (`j1b`). Each replacement:
  - announces the toast again (new `role="alert"` content);
  - replays the entry animation;
  - resets the timeout, so a toast in a parent that re-renders often may never auto-dismiss;
  - silently discards the previous `onDismiss`.
- **Masking:** the playground masks this by wrapping `onDismiss` in `useCallback` (`main.jsx:144`).
- **Verified by:** jsdom probe.
- **Suggested fix:** enqueue once on mount and keep the latest props in refs. Update content in place or re-key explicitly (for example with an `id` prop), rather than depending on callback and element identity.

### Medium

**M1. A non-modal Popover (`modal={false}`) cannot be dismissed by an outside click, or by Escape while focus is on the trigger.**
- **Where:** `overlays.mjs:316`. react-aria's `usePopover` sets `isDismissable: !isNonModal`, and non-modal mode keeps focus on the trigger.
- **Reproduction:** open with `modal={false}`, then click outside: it stays open. Press Escape on the trigger: it stays open. Only Escape from inside the popover, or toggling the trigger, closes it (`p8`).
- **Effect:**
  - Contradicts the catalog obligation "dismiss on Escape or outside focus interaction when enabled". `dismissable` defaults to true but does nothing here.
  - The canonical `AnchoredPopoverExample` uses `modal={false}`.
  - An earlier probe showed the stale non-modal popover persisting underneath a later modal Dialog.
- **Verified by:** browser probe.
- **Suggested fix:** in non-modal mode, close on outside interaction (React Aria's `useInteractOutside`) and handle Escape on the trigger, both gated on `dismissable`. Add tests.

**M2. `dismissable={false}` on Popover can be bypassed.**
- **Where:** `overlays.mjs:359`. The DialogTrigger state is passed through with no guard.
- **Cause and reproduction:**
  - A modal Popover still renders React Aria's two visually hidden "Dismiss" buttons, and activating one closes it (`openAfterHiddenDismiss: false`, `changes: [false]`).
  - In non-modal mode, toggling the trigger also closes it.
  - Dialog has a guard for exactly this case (`useDialogTriggerState`, `:236-248`). Popover does not.
- **Effect:** screen-reader users get a "Dismiss" control that defeats the contract.
- **Verified by:** jsdom probe.
- **Suggested fix:** reuse the Dialog guard for Popover's `onOpenChange` and its uncontrolled state.

**M3. Toast timers ignore hover that starts during the entry animation, and can leak a timeout that cannot be paused.**
- **Where:** `overlays.mjs:678-702`.
- **Cause:**
  - `ToastView` pauses the timer during entry, then calls `timer.resume()` unconditionally in `onEntryComplete`. That ignores the region's hover and focus pause.
  - react-stately's `Timer.resume` is not idempotent, so a hover in and out of the region during entry (which calls `resumeAll`), followed by the entry-complete resume, creates two timeouts. The first leaks and can't be paused.
- **Reproduction:**
  1. Add a toast with `duration` 1500.
  2. Move the pointer over and off the toast within the first 20 ms.
  3. After entry, hover the toast and hold.
  4. The toast closes while hovered (`leak_presentWhileHovered: 0`). The control case, hovering only after entry, stays open.
- **Why the existing test misses it:** the hover-pause test in `interaction-motion` hovers only after Playwright's stability wait, which is after entry.
- **Verified by:** browser probe.
- **Suggested fix:** track whether the region is paused before resuming, and only resume a timer this code itself paused and that is not running (for example, check `timerId`).

**M4. `disabled` on Tooltip and PreviewTrigger marks the still-working trigger `aria-disabled="true"`.**
- **Where:** `overlays.mjs:436-437`.
- **Effect:** turning off a tooltip makes assistive technology announce the button or link as unavailable, though it still activates. A MuxUI `Button` trigger gets `aria-disabled="true"` with `disabled: false`. The test asserts this behaviour (`r1-4-overlays.test.mjs:346,389`) under the title "without disabling triggers".
- **Effect on catalog:** neither catalog record states this.
- **Verified by:** jsdom probe and the existing test.
- **Suggested fix:** keep `aria-disabled` and `data-disabled` off the consumer's trigger. Use a Mux UI-owned data attribute if styling is needed.

**M5. DropZone `onActivate` fires from any nested control's click with `detail 0`, sometimes twice.**
- **Where:** `overlays.mjs:131-136,150` (the click handler sits in the capture phase on the root).
- **Reproduction:**
  - A keyboard press on a Browse `FileTrigger` inside a DropZone fires `onActivate` twice: once for the button's click, once for React Aria FileTrigger's programmatic `input.click()` (`FileTrigger.mjs:33`). Probe result: `dz_activateFiredFromInnerConsumerButton: 2`.
  - By code reading (not probed), every mouse click on that Browse button also fires it once, because the programmatic input click has `detail 0`.
- **Effect:** "DropZone containing a FileTrigger" is a common pattern.
- **Verified by:** jsdom probe plus code reading.
- **Suggested fix:** only treat the event as activation when `event.target` is React Aria's hidden drop button.

**M6. An uncontrolled Dialog with `dismissable={false}` can never close.**
- **Where:** `overlays.mjs:239-243`.
- **Reproduction:** `trigger` with no `open`, `dismissable={false}`, and `actions={<Button slot="close">OK</Button>}`. The close-slot press goes through `state.close()`, which the guard swallows. The dialog stays open (`j2_stillOpenAfterCloseSlot: true`, `changes: [true]`), so the page stays inert and focus stays trapped.
- **Effect on catalog:** the catalog only permits closing by "controlled owners". There is no runtime guard or warning, and no test.
- **Verified by:** jsdom probe.
- **Suggested fix:** let explicit close-slot and action closes through, rejecting only Escape, outside press and trigger toggle. Otherwise require `open` when `dismissable` is false (a type plus a dev error).

**M7. Focus is lost to `<body>` when the element that opened a Dialog unmounts while it is open.**
- **Where:** focus restore is React Aria's default; Mux UI adds no fallback (`overlays.mjs:250`).
- **Reproduction:** open a controlled Dialog from `#ctl-opener`. An action inside removes the opener. Press Escape: `activeElement` is `[BODY]` (`p3`).
- **Effect:** the review brief named this case, and there is no test for it.
- **Verified by:** browser probe.
- **Suggested fix:** provide a fallback target (for example the nearest focusable ancestor of where the trigger was, or a caller-provided return-focus ref), and test it.

**M8. Missing proof for these contracts:**
- **Dialog:** Tab containment, sibling `inert` and scroll lock (both work in my probe but are not asserted), positive backdrop-click dismissal, Escape order with nested overlays, restore after the trigger unmounts.
- **Popover:** modal initial focus, containment and restore; non-modal dismissal; switching `modal` while open (claimed in the catalog); hidden Dismiss buttons.
- **PreviewTrigger:** delay, close delay, warmup and safe-area timing, focus not stolen, long press.
- **Toast:** keyboard dismissal focus, hover or focus during entry, stability across re-renders, focus-pause.
- **DropZone:** real `dragenter`/`dragover`/`drop` and the drop-target state, nested consumer controls.
- **FileTrigger:** keyboard opening, and the claim that the same file can be selected again (the input reset).

### Low

- **L1. Toast `duration` is not validated** (`overlays.mjs:745`). `Infinity` or anything at or above 2^31 ms makes `setTimeout` fire almost immediately, which matches WebIDL `long` conversion. A negative value never dismisses (`Timer.resume` returns early). The other numeric props are validated with `normalizeNonNegativeFinite`. Verified by code reading only.
- **L2. A declarative Toast whose `onDismiss` unmounts it** (the playground pattern) runs `dispose(key, false)` (`:818-822`, `:648-656`). That deletes the retained exiting record, so the exit animation is cut short. Code reading.
- **L3. DropZone puts `aria-disabled` on a `<div>` with no role** (`:137-141`). ARIA 1.2 deprecates `aria-disabled` on generic elements. Code reading.
- **L4. `normalizeMaxVisible` silently turns values between 0 and 1, and negatives, into 5** instead of rejecting them (`:39-43`). Code reading.
- **L5. Dialog has no `aria-modal`.** This is React Aria's deliberate design: siblings are made inert instead (probe: the root is inert while open). The catalog says "Expose dialog and modal semantics", which would be more accurate as "modal behaviour via inert siblings".

## 3. Claims check

These catalog statements don't match the code:
- **Popover:** "dismiss on Escape or outside focus interaction when enabled" is false for `modal={false}` (M1). `dismissable` false is bypassable (M2).
- **PreviewTrigger:** "Delegate ... keyboard handling to RAC PreviewTrigger" and "dialog semantics without focus containment" don't hold; the inner Dialog overrides React Aria's rule of not moving focus on open (H1).
- **Toast:** "RAC owns ... pause/resume timing, ... focus" is undermined by the entry pause/resume (M3) and by `inert` (H2). "Toast declaratively enqueues one notification" fails across re-renders (H3).
- **Dialog:** "modal semantics" (L5). It also never states that an uncontrolled Dialog with `dismissable` false traps the user (M6).
- **Tooltip:** nothing records that `disabled` changes the trigger's semantics (M4).

The five corrections named in PR #107's description, checked against the current code:

| Correction | Status |
|---|---|
| Popover dismissal | Holds for modal Escape and outside press (tested). Incomplete per M1 and M2. |
| Toast lifecycle | Teardown (pause then clear, silent declarative teardown) holds and is tested. New defects H2, H3, M3. |
| Accessible naming | Holds: guards and Toast's "Notification" fallback title are tested. Tooltip `aria-describedby` and the Dialog name were confirmed in the browser. |
| Visibility limits | Holds: maxVisible normalization and queue displacement are tested. |
| Type/runtime alignment | Holds: the `.d.ts` for the seven families matches the runtime props and ref targets, and `tsc` passes. |

Release integrity, as far as these families go: the nine names are exported from `generated/index.mjs`, no React Aria `UNSTABLE_` or Modal names leak into exports or types, and the overlay CSS ships in `generated/styles.css`.
