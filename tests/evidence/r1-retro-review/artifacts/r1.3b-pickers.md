## 2. Findings by severity

### High

**F1. Read-only Slider, ColorSlider, ColorArea, ColorWheel and ColorSwatchPicker trap keyboard focus (WCAG 2.1.2).** A read-only ColorPicker passes the trap to the same children.
- **Where:** `packages/react/src/collections.mjs`:
  - `readOnlyInteractionEvents` includes `'keydown'` (193-196), and `setReadOnlyTargetGuard` calls `preventDefault` on every key in capture (199-212).
  - Each component also has an `onKeyDownCapture: preventReadOnlyInteraction` that blocks every key: ColorArea 395-400 and 416, ColorSlider 437-444, ColorWheel 481-502, ColorSwatchPicker 527-542, Slider 942-947 and 980.
- **Reproduction:** render `<Slider aria-label="x" readOnly defaultValue={50}/>` followed by a button. Focus the thumb and press Tab: focus stays put. Shift+Tab also stays put. ColorSwatchPicker also loses arrow-key focus movement, not just selection.
- **Verified by:** a Chrome probe (`<tmp>/r1.3b-review/case-tab.mjs`). With `readOnly: true`, focus stayed on the control after both Tab and Shift+Tab for all five. The same fixture with `readOnly: false` let Tab move to the next button.
- **Why tests miss it:** they assert that focus is kept and the value doesn't change (`r1-3-parity.test.mjs:1082-1168`, `test/browser/read-only-*.test.mjs`). None presses Tab.
- **Fix:** block only the adjustment keys (arrows, Page Up and Down, Home, End, and Enter or Space for swatches) and pointer input. Let Tab, Escape and modifier keys through. For ColorSwatchPicker, allow focus movement and block only selection. Add a browser test that presses Tab and Shift+Tab for each read-only control.

**F2. RadioGroup submits its value under a random generated key, and there's no way to name it.**
- **Where:** `collections.mjs:904` destructures a fixed prop list with no `name` and no rest spread. `collections.mjs:925` builds `AriaRadioGroup` without `name`. The type at `src/generate.mjs:655` has no `name`. `test/r1-3-parity.test.mjs:568-574` asserts that `name` is dropped.
- **Behaviour:** RAC needs a native name to group the radios, so it falls back to a `useId` value.
- **Reproduction:** put `<RadioGroup label="Density" options={…}/>` inside a `<form>` and submit. FormData contains `["react-aria7690504642-_r_t_", "a"]`.
- **Verified by:** SSR probe (`name="react-aria-_R_tH5_"`) and Chrome form probe (`case-form.mjs`).
- **Consequence:** this is a wrong form value in common use. The catalog summary says "Selects one option from a named group", and the Roadmap requires `E-R1.3-03` form behaviour.
- **Fix:** admit `name` (and probably `form`) in the catalog binding, the d.ts, and the destructure, and forward it to `AriaRadioGroup`. Replace the "name is unsupported" assertion with a FormData submit-and-reset test.

### Medium

**F3. Slider has no form participation.** Upstream number and colour range controls support names, but Mux UI admits none.
- **Where:** `collections.mjs:939, 961`; type at `generate.mjs:676`. The `name` prop lands on RAC's root group and never reaches the range input.
- **Reproduction:** `<Slider label="Volume" name="volume"/>` inside a form submits nothing.
- **Verified by:** form probe.
- **Related:** ColorSlider, ColorWheel and ColorArea (`xName` and `yName` upstream) and ColorSwatchPicker are also unnameable. That's consistent with their bindings, but it leaves `E-R1.3-03` form behaviour unproved for all scalar pickers.
- **Fix:** admit `name` on Slider (forward it to `SliderThumb`) and decide the colour controls explicitly, or record the non-support in the catalog.

**F4. Controlled "empty" values can't be expressed, and clearing a controlled ColorField flips it to uncontrolled.**
- **Where:** `dateValue` (`collections.mjs:167`) and `colorValue` (183) turn `null` and `''` into `undefined`. `mapRange` (315) does the same for ranges. RAC reads `undefined` as uncontrolled.
- **ColorField:** `onChange` emits `next?.toString()`, which is `undefined` on clear (378), but the type is `(value: string) => void` (`generate.mjs:611`).
- **Reproduction:** controlled `<ColorField value={v} onChange={setV}/>`. Clear the text and blur. `onChange(undefined)` fires, then the console warns "WARN: A component changed from controlled to uncontrolled". Typing again warns "uncontrolled to controlled".
- **Same root cause elsewhere:** Calendar, RangeCalendar and ColorSwatchPicker can't start controlled with no selection.
- **Verified by:** Chrome form probe (console warnings captured), plus code reading for the calendars.
- **Fix:** keep `null` as controlled-empty (map `null` to `null`, not `undefined`). Type the values as `string | null` and the ColorField callback as `(value: string | null)`. Test a controlled clear.

**F5. Calendar and RangeCalendar hydration breaks whenever the server's and the client's local dates differ.**
- **Where:** RAC computes "today" from the local timezone at render. Mux UI styles `[data-today]` (`styles/collections.css:98, 933`, `styles/base.css:1155`) and has no timezone or today override.
- **Reproduction:** SSR with `TZ=Pacific/Kiritimati`, hydrate in Chrome with `timezoneId: Pacific/Pago_Pago`. React logs "A tree hydrated but some attributes … didn't match": the server sends `aria-label="Today, Sunday, October 4, 2026"` and `data-today="true"`, the client expects neither, and React doesn't patch it. The cell keeps a wrong "Today" accessible name and styling.
- **Realistic case:** a UTC server and an Australian user before 10am local time. Without a `value` near a month boundary, the whole visible grid mismatches.
- **Verified by:** `<tmp>/r1.3b-review/driver-hydrate.mjs`. No test anywhere in `packages/react/test` sets a timezone.
- **Fix:** render the today marker only after mount, or accept a `timeZone`/`today` prop. Add a hydration test across two timezones.

**F6. ColorSwatchPicker ignores item `label`, so the accessible name can't be overridden.**
- **Where:** `collections.mjs:561-578`. No `colorName` is passed from `item.label`, although `MuxUICollectionItem.label` is typed (`generate.mjs:602, 619`).
- **Reproduction:** `items=[{id:'r', color:'#f00', label:'Brand red'}]` renders `aria-label="vibrant red"`.
- **Related:** RAC keys options by colour (`data-key="#FF0000FF"`), so the item `id` is ignored and two items with the same colour collide.
- **Verified by:** SSR probe.
- **Fix:** map `label` or `textValue` to `colorName`, and either reject duplicate colours or document them.

**F7. The ColorSlider catalog example is mislabelled, and the obvious fix crashes.**
- **Where:** `catalog/components/color-slider/examples/react/basic.tsx`. The generated story `r1-3-color-slider.stories.mjs` inherits it.
- **Mislabel:** the example renders `aria-label="Hue"` with the default `channel='red'`, so a control named "Hue" adjusts red (`aria-valuetext` "51, …").
- **Crash:** adding `channel="hue"` with the example's hex value throws `Unknown color channel: hue`. `channel` and `colorSpace` are typed as plain `string` (`generate.mjs:615`) and aren't validated (`collections.mjs:432, 448`).
- **Verified by:** reading the example, plus the SSR probe for the throw.
- **Fix:** correct the example (`aria-label="Red"`, or `channel="hue" colorSpace="hsl"`). Type `channel` and `colorSpace` as unions and raise a Mux UI TypeError for incompatible pairs.

**F9. Several keyboard contracts have no tests.**
- Calendar grid navigation is unproved: arrows, Page Up and Down, Shift+Page Up and Down, Home and End. My probe passed, but no repository test covers it.
- RangeCalendar keyboard range selection is unproved, although the catalog claims "Keyboard navigation selects a start and end date". Only the DateRangePicker motion test uses ArrowLeft.
- Other untested keyboard paths: ColorArea two-axis keys, ColorSwatchPicker arrows, ToggleButtonGroup arrows (only Space is tested), and Slider Page Up and Page Down.
- No family has a reset test.

### Low

- **F8. ColorWheel silently drops `label`, then throws "requires label, aria-label, or aria-labelledby"** (`collections.mjs:475-476`). The message invites the very prop it ignores. Say "aria-label or aria-labelledby".
- **F10. Colour callbacks emit CSS `rgba(…)` strings.**
  - **Where:** ColorField onChange 378, ColorArea 408, ColorSlider 452, ColorWheel 495, ColorPicker 517, ColorSwatchPicker 554.
  - **Effect:** a ColorField shows and submits `#00FF00` while its onChange emits `rgba(0, 255, 0, 1)` (form probe). It's internally consistent, but the "Core color string" format isn't specified anywhere.
- **F11. Untyped upstream props are forwarded.** The `...props` spread on ColorArea (404), ColorSlider (446), ColorWheel (489) and ColorSwatchPicker (550) passes props like `onChangeEnd`, `xChannel` and `colorSpace` to RAC. `onChangeEnd` then receives upstream `Color` objects, which contradicts the ColorSwatch rule "without exposing upstream color types" and bypasses the read-only and disabled guards. Filter these out, or admit them with string adapters.
- **F12. Dead or inert ARIA.**
  - ColorPicker puts `aria-disabled` on a role-less `div` (517). Tests also pass `aria-label` there, which ARIA 1.2 prohibits on generic elements. It may also need a `group` role and name.
  - ColorSwatch's `aria-disabled` (354) is filtered out by RAC and never reaches the DOM.
  - RadioGroup with a string label sets `aria-label` and renders a separate, unassociated span (930). The name is correct, but the visible text and the name can drift.
